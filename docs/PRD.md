# 司命（Siming）产品需求文档（PRD）

| 项 | 内容 |
|---|---|
| 文档版本 | v0.8 草稿 |
| 日期 | 2026-11-23 |
| 状态 | v1.1 MCP 完成；v2-a「提取与快捷动作」已实现 |
| 产品名 | 司命（Siming） |

## 1. 背景与问题

**现状**：本机同时有多个开发中的项目，每个项目都需要起常驻进程（`npm run dev`、后端 API、worker、mock server……）。日常操作是：开终端 → `cd` → 跑命令 → 改完代码 `Ctrl+C` → 重新跑。

| # | 痛点 | 具体表现 |
|---|---|---|
| P1 | 终端窗口堆积 | 5 个项目 = 5 个终端，任务栏找不到谁是谁 |
| P2 | 状态不可见 | 记不清某个服务到底起没起、是不是上次那个进程 |
| P3 | 停止不彻底 | 关终端后子进程还占着端口，下次启动报 `EADDRINUSE` |
| P4 | 重启成本高 | 每次都要回终端 `Ctrl+C` + 上箭头 + 回车 |

## 2. 产品定位

**一句话**：面向开发者的托盘进程开关面板 —— 把「cd 到项目、跑命令、Ctrl+C、再跑一遍」压缩成托盘里的两次点击。

- **性质**：Windows 桌面软件，常驻托盘，本地个人工具
- **目标用户**：同时维护多个项目的开发者
- **边界**：只负责进程的**启动 / 停止 / 重启**，以及**进程级状态**（在跑还是没跑）
- **不负责**：进程内部状态、build 流程、健康检查、崩溃拉起、日志语义
- **提取的定位**：v2 允许用户用正则从输出里搬运字符串，但司命**不解释其含义**，也不据此判断进程是否就绪——取什么、怎么用，全由用户的配置决定

> 心智模型：一堆带状态灯的 `.bat` 快捷方式，放进托盘，且能真正停干净。

**命名**：司命，取自《楚辞·九歌》的《大司命》《少司命》。"司命"即掌管性命——正好对应本软件唯一的权力：进程的启动与终止。拼音短名 `Siming`，用作 exe、仓库与命名空间。

## 3. 使用场景

- **S1 多项目常驻**：前端 dev server、后端 API、worker 各一条，托盘里一眼看清谁在跑
- **S2 快速重启**：改完配置/代码，右键条目 → 重启，不用回终端
- **S3 临时常驻工具**：frp、本地 mock、隧道工具，用完即停
- **S4 收工清零**：托盘菜单「全部停止」，确认没有偷跑的进程

## 4. 成功指标（个人工具，定性为主）

- 从托盘启动任意条目 ≤ 2 次点击
- 停止后 3 秒内端口释放，任务管理器无残留子进程
- 常驻内存 < 80 MB，空闲 CPU ≈ 0
- 日常启停全程不需要打开终端窗口

## 5. 产品形态

- **托盘图标**：常驻；左键打开主窗口，右键菜单为条目列表 + 全局操作
- **主窗口**（按需打开）：条目列表（名称 / 状态 / cwd / 命令）、启停按钮、配置编辑
- **日志窗口**（按需打开）：单条目，最近 200 行，只读
- **条目快捷动作**（v2）：条目子菜单底部可追加动作项，绑定从输出里提取的字段（如链接、密码），一键打开或复制
- **无主窗口常驻概念**：关闭主窗口 = 收进托盘，不退出

## 6. 功能需求

### 6.1 条目与配置

| ID | 需求 | 验收标准 |
|---|---|---|
| FR-01 | 配置固定为 exe 同目录的 `processes.json`（绿色便携，不写 `%APPDATA%`） | 文件不存在时自动创建空配置 |
| FR-02 | 路径不可配置；界面只读展示完整路径，并提供「打开所在文件夹」 | 路径按 exe 所在目录解析，不受启动时工作目录影响 |
| FR-03 | 外部编辑配置文件后自动重载（运行中条目不受影响） | 保存后 1s 内列表更新 |
| FR-04 | 解析失败时保留上一份可用配置，并提示错误位置 | 坏 JSON 不导致软件崩溃 |
| FR-05 | 界面增删改条目：名称 / cwd / 命令 / shell / env；「随司命启动」改在托盘菜单切换 | 保存后写回 JSON，2 空格缩进 |
| FR-06 | 校验：名称非空且唯一、cwd 存在、命令非空、shell 合法 | 不合法不允许保存 |
| FR-07 | 删除运行中条目：先确认，确认后停止再删除 | 不留孤儿进程 |
| FR-08 | 条目顺序 = 配置文件顺序，界面支持上移/下移 | 写回后顺序保持 |

> 界面新增/编辑条目时，若缺少 `id` 会自动生成并回写，确保改名不改变运行时身份。

### 6.2 进程控制

| ID | 需求 | 验收标准 |
|---|---|---|
| FR-09 | 启动：在条目 cwd 下，按 `shell` 执行命令，输出接入日志 | 已在运行时不重复启动 |
| FR-10 | 停止：先尝试优雅中断（Ctrl+C），超时 5s 后强制结束**整棵进程树** | 端口释放、无残留子进程 |
| FR-11 | 重启 = 停止并等待完全退出 → 启动 | 连续重启 3 次不出现端口冲突 |
| FR-12 | 全部启动 / 全部停止（托盘菜单与主窗口） | 逐个执行，失败不阻塞其余条目 |
| FR-13 | 进程自行退出：状态回到「已停止」，记录退出码与时间，**不自动重启** | 退出码可在悬停/详情查看 |
| FR-14 | 启动失败（cwd 不存在、shell 不存在、命令无法执行）：状态为已停止，日志给出错误 | 不弹模态框打断批量启动 |

### 6.3 状态与托盘

| ID | 需求 | 验收标准 |
|---|---|---|
| FR-15 | 状态四态：已停止 / 启动中 / 运行中 / 停止中 | 状态由进程句柄事件驱动，不轮询 |
| FR-16 | 托盘菜单列出全部条目，带状态点；条目子菜单：启动 / 停止 / 重启 / 查看日志 | 运行中才可停止，已停止才可启动 |
| FR-17 | 托盘图标 tooltip 显示「运行中 N 个」 | 状态变化后即时刷新 |
| FR-18 | 左键托盘 = 显示/聚焦主窗口；关闭主窗口 = 隐藏 | 不退出进程 |
| FR-19 | 单实例：重复启动时唤起已有实例 | 第二个进程立即退出 |
| FR-20 | 开机自启可开关（默认关） | 写入当前用户启动项 |
| FR-21 | 条目级 `autoStart`：软件启动后自动拉起（默认关）；在托盘条目子菜单里勾选切换，立即写回配置 | 仅启动一次，不循环；保存失败时回滚勾选并提示 |

### 6.4 日志

| ID | 需求 | 验收标准 |
|---|---|---|
| FR-22 | 每条目内存环形缓冲，默认最近 200 行（可配 100–5000） | 超限丢弃最旧行 |
| FR-23 | 日志窗口只读、等宽字体、自动滚底；可暂停滚动、复制、清空 | 暂停时新日志不打断阅读 |
| FR-24 | stdout / stderr 合并按行展示，保留原始顺序 | 高频输出不阻塞 UI |
| FR-25 | 剥离 ANSI 转义序列；输出编码默认 UTF-8，可按条目配置 `gbk` | 中文不乱码 |
| FR-26 | 日志不落盘，退出即失（v1） | — |

### 6.5 退出行为

| ID | 需求 | 验收标准 |
|---|---|---|
| FR-27 | 主动退出：若有运行中进程，弹窗三选一 —— **结束所有并退出（默认）** / 保留进程并退出 / 取消 | 弹窗显示运行中数量 |
| FR-28 | 「保留进程」语义 = 进程继续跑，但脱离本软件管理；下次启动不自动接管 | 选项文案明确说明 |
| FR-29 | 系统注销/关机、软件崩溃：由 Job Object kill-on-close 兜底结束全部子进程 | 无残留（进程管理器验证） |

### 6.6 配置示例

```json
{
  "version": 1,
  "settings": {
    "logLines": 200,
    "startWithWindows": false
  },
  "entries": [
    {
      "id": "blog-dev",
      "name": "Blog Dev",
      "cwd": "D:\\projects\\blog",
      "command": "npm run dev",
      "shell": "cmd",
      "encoding": "utf-8",
      "env": { "PORT": "3000" },
      "autoStart": false
    }
  ]
}
```

- `shell`：`pwsh` / `powershell` / `cmd` / `none`（直接执行 exe）；新建条目按 pwsh → powershell → cmd 取第一个可用的
- `id`：可省略，省略时按 `name` 生成并回写
- `env`：合并进当前进程环境，不覆盖系统环境
- `extract` / `actions`：可选，分别配置字段提取与快捷动作，见 §6.7

### 6.7 提取与快捷操作（v2）

条目除了启停，还能从**自己的输出**里取出少量字段，并把这些字段绑定成托盘菜单里的固定动作。不另起进程、不轮询、不做脚本引擎。

数据流向：

```
子进程 stdout/stderr → 按行读入 → 剥 ANSI + 按条目编码解码 → 逐行匹配 extract → 命中即更新变量表
                                                                        ↓
                                              托盘菜单打开时读变量表快照 → 置灰 / 可用
```

#### 6.7.1 字段提取 `extract`

```json
"extract": {
  "url": "server listening on (https?://\\S+)",
  "password": { "regex": "server password (\\S+)", "secret": true },
  "port": { "regex": "listening on .*:(\\d+)", "mode": "latest" }
}
```

字符串简写等价于 `{ "regex": "..." }`，字段名即变量名。

| 项 | 规则 |
|---|---|
| 数据来源 | 条目自身的 stdout / stderr，逐行、实时；输入已剥离 ANSI、已按条目 `encoding` 解码 |
| 匹配 | 每字段一条 .NET 正则；取第 1 个捕获组，没有捕获组时取整个匹配 |
| 多行 | **不支持**。一条日志行就是一次匹配的边界 |
| 不匹配 | 不写入。捕获为空或纯空白也不写入，避免噪声把好值冲掉 |
| 变量名 | `[A-Za-z0-9_-]+`，不得与内置占位符（`cwd` `pid` `name` `id` `state`）重名 |
| 生命周期 | 条目启动前与回到「已停止」时都清空全部值，`first` 字段的冻结标记一并复位 |
| 热重载 | 某字段的正则变更时，复位该字段的值与冻结标记 |
| 非法正则 | 只标记该字段无效并跳过，不影响其他字段、日志与条目启动 |

`mode`：

| 值 | 行为 | 适用 |
|---|---|---|
| `first`（默认） | 首次命中后冻结，不再解析，直到条目重启 | 密码、只打印一次的地址 |
| `latest` | 每行都比对，最后一次命中胜出 | 端口会变、`dotnet watch` 热重载 |

> 默认 `first` 不只是省几次正则调用：它同时防止后来的噪声行覆盖已经拿到的好值（例如重连失败时打印的空密码）。

`secret`：该字段的值不进入诊断信息、控制接口与 MCP，唯一的出口是显式绑定它的动作。注意它不约束程序自己打印的原文——那一行本来就在日志里，日志窗口照常可见。`

#### 6.7.2 动作 `actions`

```json
"actions": [
  { "label": "打开链接", "type": "open", "target": "${url}" },
  { "label": "复制链接", "type": "copy", "text": "${url}" },
  { "label": "复制密码", "type": "copy", "text": "${password}" }
]
```

**占位符**：`${<extract 键>}`，以及内置的 `${cwd}` `${pid}` `${name}` `${id}` `${state}`。

**拼接在动作侧完成，不在提取侧**：提取只负责单一事实，动作负责拼表达。

```json
"extract": {
  "host": "listening on https?://([\\d.]+):",
  "port": "listening on https?://[\\d.]+:(\\d+)"
},
"actions": [
  { "label": "打开链接", "type": "open", "target": "http://${host}:${port}" }
]
```

**模板中任一变量无值 → 整个动作置灰，不隐藏。** 这一条同时覆盖「还没提取到」和「条目已停止」两种情况。

**动作类型（仅此三类）**：

| type | 行为 | 可用条件 |
|---|---|---|
| `open` | 用默认程序打开 URL 或路径 | 模板变量齐全 |
| `copy` | 把模板结果复制到剪贴板 | 模板变量齐全 |
| `command` | 在 cwd 下按条目 shell 执行命令 | 模板变量齐全，且条目运行中 |

`command` 的生命周期：挂进条目自己的 Job Object，输出并入条目日志，条目停止时一并终止，不产生独立状态或临时任务。

> **分期**：v2-a 只实现 `open` / `copy`。`command` 推迟到 v2-b —— 它要求打破「一条目一进程」的运行时假设（`EntryRuntime` 目前只有一个 `Launched` / `ExitSignal` / `State`），需要独立的附属进程模型与并发设计。

#### 6.7.3 菜单渲染

- 动作**平铺**在条目子菜单里，不套「其他」之类的子菜单：多一层悬停的代价高于菜单变长
- 有 `actions` 才追加动作项；没有就不加分隔线，也不留空组
- 位置固定：条目子菜单最底部，前面一条分隔线
- 顺序 = `actions` 数组顺序
- **结构由配置决定，可用性由运行时决定**：菜单里不增删项，只在做不了时置灰
- 提取值只在运行期有效：条目停止即清空，因此绑定提取变量的动作全部置灰
- 不展示提取值本身：不显示地址、不显示密码明文；密码只经「复制密码」进入剪贴板
- 动作不进入进程状态机；执行失败只出托盘气泡，不影响条目状态
- 建议动作控制在 3–5 项：再多样子菜单会被拉长，但仍按配置原样显示

| ID | 需求 | 验收标准 |
|---|---|---|
| FR-30 | 条目可选 `extract`，从其自身 stdout/stderr 逐行提取命名变量；输入已剥离 ANSI、按条目编码解码 | 彩色输出与 GBK 输出均可正确提取 |
| FR-31 | 每字段一条正则，取第 1 捕获组；不匹配或捕获为空时不写入 | 无关日志与失败重连行不会冲掉已提取的值 |
| FR-32 | `mode: first`（默认）命中一次后冻结；`mode: latest` 每次命中都更新 | `dotnet watch` 换端口后 `latest` 跟随、`first` 保持原值 |
| FR-33 | 条目启动前与回到「已停止」时都清空提取值；热重载中正则变更时复位该字段 | 停止后旧值不可复制，重启后不残留上一轮的地址与密码 |
| FR-34 | 提取在输出线程内完成，单次匹配超时 100ms，超长行跳过；任何提取异常不得影响日志与进程状态 | 病态正则不会冻结日志窗口，子进程不因管道写满而假死 |
| FR-35 | 条目可选 `actions[]`，类型 `open` / `copy` / `command`，模板可引用提取变量与内置占位符 | 三类动作按定义执行 |
| FR-36 | 拼接在动作侧完成；任一引用变量无值时整项置灰而非隐藏 | 未提取到 `url` 时「打开链接」为灰、不消失 |
| FR-37 | 动作项平铺在条目子菜单底部（前置分隔线）；无 `actions` 时不追加 | 不出现空分组；菜单层级不随动作数量变化 |
| FR-38 | 动作不进入进程状态机；执行失败只出气泡 | 动作失败后条目状态、运行时长与日志均不变 |
| FR-39 | `secret` 字段的值不进入诊断信息、控制接口与 MCP，唯一出口是绑定它的动作 | 控制接口与 MCP 均查不到提取值 |
| FR-40 | 本期 MCP 不提供动作触发，也不返回提取值 | `siming_*` 工具列表中没有动作或提取相关工具 |

### 6.8 MCP 接入（v1.1）

| ID | 需求 | 验收标准 |
|---|---|---|
| FR-41 | 同一份 `Siming.exe` 以 `--mcp` 启动 stdio MCP 服务，工具覆盖 list / add / update / remove / start / stop / restart / logs | AI 客户端可完成条目增删改查与启停，无需单独的服务 exe |
| FR-42 | 主程序运行时经本机控制接口操作；未运行时配置类工具直接读写 `processes.json`，控制类工具自动拉起主程序 | 未运行时可添加条目；start 能自动拉起并执行 |
| FR-43 | 控制接口只绑定 `127.0.0.1:17321`，使用同目录 `mcp.token` 鉴权 | 外部机器不可访问；错误令牌被拒绝 |
| FR-44 | MCP 模式与托盘主程序打包为同一个 exe；默认框架依赖发布，另提供 `-SelfContained` 自包含发布 | 发布目录只有一个 `Siming.exe`；两种发布方式均可连通 MCP |

## 7. 非功能需求

- **NFR-01 平台**：Windows 10/11 x64
- **NFR-02 性能**：常驻内存 < 80 MB；主窗口打开 < 1s；100 条目列表流畅
- **NFR-03 可靠性**：单个条目异常不影响其他条目与主程序；停止必达
- **NFR-04 日志吞吐**：持续 10k 行/分钟时 UI 不卡、内存不涨
- **NFR-05 离线性**：全功能离线；无遥测、无网络请求
- **NFR-06 安全**：本地信任模型，命令即用户自写；不做沙箱，不自动提权
- **NFR-07 便携**：配置与程序同目录，不写 `%APPDATA%` / 注册表（开机自启项除外）；拷贝整个目录即可迁移
- **NFR-08 提取开销**：空闲条目零正则调用；`first` 字段全部命中后该条目停止匹配；每行匹配 < 1ms，不阻塞日志读取与 UI
- **NFR-09 隐私**：提取值只存在内存中，不落盘；`secret` 字段的值不进入诊断信息、控制接口与 MCP

## 8. v1 范围外

自动重启 / 退避重试、健康检查、端口检测与展示、文件监听与自动 rebuild、build 流水线、日志持久化与轮转、进程组依赖与编排、远程/SSH、Windows 服务、管理员权限启动、定时任务、条目分组/标签、**脚本引擎与插件 API**（自定义菜单只做声明式提取与快捷动作，见 §6.7）、接管「保留」的脱离进程、i18n、主题、自动更新、远程 MCP（HTTP/SSE，v1.1 仅本机 stdio）。

## 9. 技术决策（已定）

| 决策点 | 结论 |
|---|---|
| 平台 | 仅 Windows |
| 壳 | .NET 10 + **WinForms**（内置 `NotifyIcon` + `ContextMenuStrip`，不引第三方托盘库） |

## 11. 风险与对策

| 风险 | 对策 |
|---|---|
| Windows 进程树杀不干净（端口占用） | Job Object 整树终止；验收用 `npm run dev` 实测 |
| Ctrl+C 对部分程序无效 | 5s 超时后强杀；UI 明示「已强制结束」 |
| `cmd /c` 引号与中文路径踩坑 | 命令整体交给 shell 字符串；用中文路径 + 带空格路径做验收 |
| 中文输出乱码（GBK/UTF-8 混合） | 条目级 `encoding` 配置，默认 UTF-8 |
| exe 放在 `Program Files` 等只读目录时无法写配置 | 启动时探测目录写权限，明确提示「请移到可写目录运行」 |
| 「保留进程」与崩溃兜底冲突 | 正常退出路径显式清标志；崩溃路径保持 kill-on-close |
| 「保留进程」后输出管道随软件关闭 | 已记录风险；v2 可考虑改为输出落盘后再脱离 |
| 200 行日志不足以排查 | 上限可配到 5000；v1 不做落盘 |
| 托盘应用被安全软件误报 | 不做注入、不写注册表敏感项；发布签名（后续） |
| MCP 控制接口端口被占用 | 主程序状态栏提示；MCP 退回配置模式，启停不可用 |
| AI 客户端仍配置旧 `Siming.Mcp.exe` | 文档要求改为 `Siming.exe` + `args: ["--mcp"]`；发布脚本会尝试清理旧 exe |
| 病态正则回溯卡住输出线程，进而冻住日志、写满管道拖死子进程 | `MatchTimeout` 100ms + 行长上限 + 用构造的病态正则做验收 |
| 程序检测 TTY，管道下不打印目标行，提取永远为空 | 文档要求先用管道验证；不做兜底，菜单置灰即为信号 |
| 热重载改了正则却不生效（该字段早已冻结） | 正则变更时复位该字段的值与冻结标记 |
| 提取到上一轮的旧端口并被误用 | 条目启动清空；端口类字段用 `mode: latest` |
| 用户误以为提取值会落盘或可回看 | 明确「只存内存、重启即失」；主窗口不展示提取值 |

## 12. 验收清单（手动）

1. 配置 `npm run dev`（cwd 为中文且含空格路径）→ 启动 → 页面可访问
2. 停止 → 端口释放、任务管理器无残留 node/esbuild 进程
3. 连续重启 3 次，无端口冲突
4. 进程自行退出 → 状态变「已停止」，退出码正确，日志保留
5. 托盘右键重启，全程不打开主窗口
6. 退出选「结束所有」→ 无残留；选「保留」→ 进程仍在跑，软件重开后显示已停止且文案已说明
7. 外部编辑 `processes.json` → 列表 1s 内更新；写坏 JSON → 保留旧配置并提示
8. 高频日志（`1..100000` 循环打印）下 UI 可操作、内存稳定
9. 注销/关机时无残留进程
10. 整个程序目录拷到另一路径 → 条目与设置随 `processes.json` 一起走，无 `%APPDATA%` 残留
11. 配置 `extract` 抓 `server listening on (https?://\S+)` 与 `server password (\S+)` → 启动目标程序后动作项由全灰变可用，打开/复制结果正确
12. 停止该条目 → 三项全部置灰；重启后旧值不残留，新地址重新填充
13. 把地址字段改成 `mode: latest`，在 `dotnet watch` 热重载换端口后菜单跟随新端口；`first` 则保持原值
14. 写入病态正则（如 `(a+)+$`）并灌入超长日志行 → 日志不卡、条目状态正常、该字段保持为空
15. 日志窗口与 MCP 工具输出中都查不到 `secret: true` 字段的值

## 13. 开放问题

- Q1 「保留进程」后是否需要「疑似仍在运行」提示，或按 PID 重新接管？（v1 建议不做）
- Q2 日志 200 行是否作为默认值即可，还是直接给 500？
- Q3 停止是否需要二次确认？（建议默认不确认，托盘操作要快）
- Q4 条目是否需要颜色/图标/分组来区分项目？（v1 建议不做）
- Q5 提取值是否需要在主窗口可见（如加一列「地址」）？（本期不做，菜单是唯一出口）
- Q6 `command` 类型动作是否值得做？（需打破「一条目一进程」的运行时假设，v2-b 再评估）
- Q7 是否需要跨条目引用变量（如一个全局地址被多处复用）？（本期不做）
- Q8 `first` 字段冻结后，若程序重连拿到新值，是否需要「手动清空/刷新该字段」的入口？（本期接受「重启才更新」）
